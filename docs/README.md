# CloudGuard 핵심 설명

**이 문서가 필요한 이유:** 루트 README의 비용 수집과 예산 계산을 내 말로 설명하기 위한 짧은 보충 자료입니다. 먼저 [프로젝트 소개](../README.md)를 보고, 아래 세 가지를 이해한 뒤 [확인 결과](VERIFICATION.md)를 읽습니다.

## 1. 비용은 어떻게 저장하고 조회하나요?

AWS Cost Explorer에서 일별 비용을 가져와 날짜와 서비스별로 정리합니다. 서비스는 EC2, RDS, S3, OTHER로 구분하고, 직접 입력한 비용과 AWS 비용은 출처를 구분해 저장합니다.

월 조회에서는 해당 월의 비용 기록을 DB에서 가져와 Java 코드로 합산합니다. 수동 비용과 AWS 비용을 모두 더하고, 등록한 월 예산과 비교해 사용률과 상태를 반환합니다. 예산은 이 앱의 계산 기준이며 AWS Budgets에 알림을 만드는 기능은 아닙니다.

Controller는 요청을 받고, Service는 수집과 계산 규칙을 처리하고, Repository는 DB 저장과 조회를 담당합니다.

## 2. 같은 기간을 다시 가져와도 왜 비용이 두 배가 되지 않나요?

예를 들어 같은 날짜의 EC2 비용 10.5를 다시 추가하면 합계가 21이 됩니다. 이를 막기 위해 **날짜, 서비스, AWS 출처**가 같은 기록을 먼저 찾습니다. 없으면 추가하고, 있으면 그 기록의 금액을 바꿉니다.

AWS 금액이 10.5에서 12로 바뀌면 기존 한 건을 12로 갱신합니다. 수동 기록은 출처가 다르므로 이 갱신 대상에 들어가지 않습니다. 다만 월 합계에는 두 출처가 모두 포함되므로, 같은 비용을 수동으로도 입력하면 함께 더해집니다.

이 방식은 첫 수집이 끝난 뒤 다시 수집하는 조건에서 확인했습니다. 두 요청이 동시에 실행되는 상황의 중복 방지까지 해결한 것은 아닙니다.

관련 코드: [기존 기록 조회와 갱신](../src/main/java/com/cloudguard/cloudguard/cost/service/CostService.java)

## 3. 예산 상태는 왜 반올림한 사용률로 정하지 않나요?

예산 100에 비용 69.999라면 표시용 사용률은 70%로 반올림될 수 있지만 실제 비용은 아직 70% 미만입니다. 표시용 계산과 상태 판정을 분리해, 상태는 원래 비용과 예산을 비교하도록 했습니다. 금액 계산에는 소수를 다루는 `BigDecimal`을 사용합니다.

| 실제 예산 사용 비율 | 상태 |
| --- | --- |
| 70% 미만 | SAFE, 정상 |
| 70% 이상, 85% 미만 | CAUTION, 주의 |
| 85% 이상, 100% 미만 | WARNING, 경고 |
| 100% 이상 | EXCEEDED, 예산 도달 또는 초과 |

관련 코드: [예산 상태 판정](../src/main/java/com/cloudguard/cloudguard/budget/domain/BudgetPolicy.java)

## 말로 정리해 보기

> AWS 비용을 저장하고 월 예산과 비교하는 서비스입니다. 같은 기간을 다시 수집하면 기존 AWS 기록을 갱신해 비용이 중복되지 않게 했습니다. 또 표시용 반올림 때문에 상태가 잘못 바뀌지 않도록 원래 금액으로 판정했습니다. 테스트뿐 아니라 실제 AWS 비용을 가져와 DB 기록과 API 응답도 확인했습니다.

위 문장을 읽은 뒤, 문서를 덮고 “기존 기록을 찾는 기준”, “수동 비용을 구분하는 이유”, “69.999를 SAFE로 판단하는 이유”를 설명해 봅니다.
