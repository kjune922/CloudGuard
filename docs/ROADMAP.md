# CloudGuard 확장 계획

월 비용을 확인하는 API에서 비용, 예산을 관리하는 서비스로 발전시키려 합니다. 정확성과 재현성을 먼저 마무리하고, 사용 화면과 운영 경험을 차례로 추가합니다. 아래 항목은 개발 계획입니다.

## 1 비용과 예산의 정확성

| 작업 | 완료 기준 | 포트폴리오에 남길 근거 |
| --- | --- | --- |
| 예산 상태 판정과 표시용 반올림 분리 | 69.999/70, 84.999/85, 99.999/100과 소수 예산의 경계값 검증 | 실패 재현 테스트, 수정 코드, 통과 결과 |
| 동시 AWS 수집 정책과 저장 제약 | 독립 트랜잭션의 동시 요청에서 AWS 기록 1건 유지. 수동 다건 등록 보존 | MySQL 동시 테스트와 선택한 충돌 정책 |
| 사라진 항목, 0, 음수 비용 정책 | 재수집 스냅샷의 의미와 지원 비용 종류 결정, 중간 실패 롤백 검증 | 정책별 입력, 저장 결과 표 |

재현 조건과 구현 선택지는 [READINESS](READINESS.md)에 정리했습니다. 첫 작업은 예산 반올림 경계값 수정으로 잡습니다.

## 2 새 환경에서 재현되는 실행과 검증

MySQL Testcontainers로 Flyway V1, `ddl-auto=validate`, 금액 정밀도와 저장 제약을 검증합니다. PR용 테스트 CI를 만들고 배포 CI와 분리합니다. AWS 조회, 변환과 저장 트랜잭션의 책임도 나눕니다.

완료 기준은 새 환경에서 README 절차로 실행되는 것, PR 테스트 통과, 외부 조회 실패 시 DB 변경 없음, 저장 중간 실패 시 롤백입니다. 실제 배포는 ECR, SSM 성공 기록과 이전 이미지 복구 절차를 확보한 뒤 완료로 표시합니다.

## 3 비용과 예산을 한 화면에서 관리

처음 화면은 월 선택, 총 비용, 서비스별 비용, 예산과 사용률을 보여주는 대시보드로 구성합니다. 수동 비용 등록, 예산 변경, 지정 기간 AWS 수집을 연결합니다. Thymeleaf 등 기존 Spring MVC와 연결하기 쉬운 방식으로 시작할 수 있습니다.

| 화면 흐름 | 확인할 결과 |
| --- | --- |
| 월 선택 → 월별 비용 조회 | 월 변경에 따라 총액, 서비스별 금액, 예산 상태 표시 |
| 비용 등록 또는 AWS 재수집 → 새로 조회 | 금액과 예산 상태가 함께 갱신됨 |
| 예산 변경 → 상태 확인 | 새 예산을 기준으로 상태 재계산 |
| 잘못된 입력, 미등록 예산 | 사용자에게 처리 가능한 오류 안내 |

완성 후 직접 실행한 화면 캡처와 짧은 데모를 README에 추가합니다. 샘플 데이터는 샘플임을 표시합니다. 화면만으로 데이터가 실제 저장됐다고 판단하지 않고 API, DB 결과와 함께 확인합니다.

## 4 운영 사례를 한 가지씩 추가

사용자, AWS 계정별 구분은 별도 설계가 필요합니다. 인증, 권한과 소유 범위를 먼저 정한 뒤, 자동 수집, 알림을 연결합니다. 모든 기능을 한 번에 추가하기보다 설명하고 재현할 수 있는 사례 하나를 완성합니다.

| 확장 후보 | 선행 조건 | 검증할 질문 |
| --- | --- | --- |
| 사용자, 계정별 비용과 예산 | 인증, 소유자 식별, 자격 증명 관리 방식 | 다른 사용자의 데이터 접근을 어떻게 차단하는가? |
| 정기 수집과 실행 이력 | 동시 수집 정책, 기간 정책, 외부 호출 실패 처리 | 중복 실행과 실패 후 재시도에서 결과가 유지되는가? |
| 예산 알림 | 상태 변화 정책, 발송 이력과 중복 방지 | 같은 상태를 반복 조회해도 알림이 중복되지 않는가? |
| 월 집계 쿼리 개선 | 정확한 기준 결과와 측정 데이터 | Java 합산과 DB 집계의 결과, 실행 계획, 응답 시간이 어떻게 다른가? |

## README와 포트폴리오 갱신

README에는 서비스 소개, 현재 구조, 대표 검증 결과만 남깁니다. 세부 API는 RUNBOOK, 구현 판단과 테스트는 PORTFOLIO, 개발 과정은 DEVELOPMENT_LOG에 기록합니다.

기능을 완료할 때는 같은 변경에서 도표와 본문을 갱신하고 코드, 테스트 링크를 연결합니다. 제출용 포트폴리오는 프로젝트 소개 1쪽과 핵심 STAR 사례 3쪽을 기본으로 삼습니다. 새 기능은 결과와 근거가 확보됐을 때 기존 사례를 보완하거나 교체합니다.
